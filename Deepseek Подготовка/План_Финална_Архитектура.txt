# Архитектурен анализ — преди да пиша какъвто и да е код

## 1. Какво имаме сега (файлова карта)

```
┌─────────────────────────────────────────────────────────────┐
│  data/                                                       │
│  ├── steps.js          (160 STEPS точки)                     │
│  ├── tasks_data.js     (4 tasks с toolkit per task)          │
│  └── plan_phases.js    (25 седмици, main + secondary)        │
└─────────────────────────────────────────────────────────────┘
                            ↑
                    (никой backend не чете!)

pipeline/
├── config.py               ← paths (единствен source of truth)
├── config.json             ← AI models, budgets
├── personas.py             ← AI personas
├── prompts.py              ← article prompts
│
├── pdf_chunker.py          ← STEPS: чете директно от data/steps.js
├── pipeline.py             ← STEPS: чете от data/steps.js
├── problem_generator.py    ← STEPS: чете от data/steps.js  
├── gap_worker.py           ← STEPS: чете от data/steps.js
├── daily_verifier.py       ← STEPS: чете от data/steps.js  
│                          ⚠ hardcoded week→phase logic (НЕ ползва PLAN_PHASES)
├── master_orchestrator.py  ← чете state files, НЕ знае за план
│
└── (липсва plan.py!)       ← никой не чете tasks_data.js / plan_phases.js
```

## 2. Проблеми, които виждам

| # | Проблем | Последица |
|---|---|---|
| 1 | 5 файла парсват `data/steps.js` независимо | DRY violation. Ако regex-ът се счупи, 5 файла се чупят |
| 2 | `tasks_data.js` и `plan_phases.js` = **само UI** | Backend не знае за Task/Level/Phase |
| 3 | `daily_verifier` hardcode-ва `week→phase` | "Седмица 2 = Phase 1" в код, не от `plan_phases.js` |
| 4 | `pipeline.py` генерира по STEPS ID в азбучен ред | Не знае кой е P1 (regional) и кой е P4 (extra) |
| 5 | Никой не проверява "Task 1 е готов" | Verifier проверява "10 случайни" |
| 6 | `master_orchestrator` не знае "днес какво е приоритет" | Пуска всичко в един ред без оглед на фокус |

## 3. Предложена архитектура

### Нов файл `pipeline/plan.py` — single source of truth за всичко план-свързано

```
pipeline/plan.py  (≈ 250 реда)
├── Парсва data/steps.js        → steps_points: dict[id → {title, desc}]
├── Парсва data/tasks_data.js   → tasks: dict[num → {name, toolkit, ...}]
├── Парсва data/plan_phases.js  → phases: list[{num, weeks, ...}]
│
├── API:
│   get_all_points()                    → list[160 ids]
│   get_toolkit(task_num)               → list[ids] (за Task 1 = 1.1-1.11)
│   get_level_points(level_id)          → list[ids] (за Level 1 = всички regional)
│   get_priority(level_id)              → list[ids] (union на toolkits ∩ level)
│   get_task_for_week(week)             → task_num  (от PLAN_PHASES)
│   get_current_week()                  → int  (дни от planStartDate / 7)
│   get_current_focus()                 → "Task 1"  (task_for_week + план)
│   get_exam_dates()                    → {regional, national}
│
└── Кешира резултатите при първо извикване
```

### Кой какво вика

| Файл | Днес | След `plan.py` |
|---|---|---|
| `pdf_chunker.py` | `load_steps_info()` — свой парсер | `plan.get_all_points()` — за classify context |
| `pipeline.py` | Свой парс на STEPS | `plan.get_toolkit(task)` за `--task 1`; `plan.get_priority(level)` за `--priority p1` |
| `problem_generator.py` | Свой парс | Същото |
| `daily_verifier.py` | Hardcoded week→phase | `plan.get_current_focus()` + `plan.get_toolkit(task)` за `audit_task_completion()` |
| `gap_worker.py` | Свой парс | `plan.get_all_points()` за coverage |
| `master_orchestrator.py` | Не знае за план | `plan.get_current_focus()` — "днес фокус = Task 1" |

### Какво остава в `config.py` vs `config.json` vs `plan.py`

| Файл | Отговорност |
|---|---|
| `config.py` | **Пътища** (data/, generated/, state/) |
| `config.json` | **AI models, budgets, watch folders** |
| `plan.py` | **Учебен план** (STEPS, TASKS, PHASES, priority) |

Ясна граница. `plan.py` е read-only от `data/`.

## 4. Въпроси, които трябва да решим ПРЕДИ код

### Q1: Кой е "current target level"?

`plan.current_focus()` трябва да знае за кого се готви student-ът. 3 варианта:

| Опция | Как работи | Кога е ок |
|---|---|---|
| **A. Calendar-driven** | `< 60 дни до regional` → focus Level 1; `< 60 дни до national` → Level 2; иначе Level 1 | Просто, но brute-force |
| **B. Config-driven** | `config.json: "target_level": "regional"` | Ясно, но ръчно сменяне |
| **C. UI-driven** | `data/steps.js` има `currentLevel` поле | Правилно, но изисква синхронизация |

**Моята препоръка: A + B.** Calendar-driven по подразбиране, config override ако искаш.

### Q2: Какво значи "Task 1 е готов"?

Възможни дефиниции:

| Опция | Дефиниция | Cost за проверка |
|---|---|---|
| **A. Article ready** | Всички toolkit точки имат `status=new` статия | 0 API calls |
| **B. Anchors ready** | Всички имат ≥3 verified anchors | 0 API calls |
| **C. Full ready** | A + B + ≥3 practice problems + verifier score ≥7 | малко API |
| **D. Student-ready** | C + AI симулира "ученик може да реши 2/3 задачи" | много API |

**Моята препоръка: C за начало.** A+B е твърде плитко. D е скъпо.

### Q3: Персистира ли се task completion?

| Опция | Какво | Pros / Cons |
|---|---|---|
| **A. Derived** | Verifier проверява файловете всеки път | Fresh, но ~100ms за 160 точки |
| **B. Persisted** | `generated/plan_state.json` — `{task: 1, complete: false}` | Fast, но старее |

**Моята препоръка: A.** 100ms е нищо. Никога не старее.

### Q4: Какво прави orchestrator-ът с plan-а?

| Опция | Какво | Пример |
|---|---|---|
| **A. Plan-aware** | Orchestrator решава "днес — P1"; пуска pipeline с `--priority p1` | Интелигентно, но orchestrator става сложен |
| **B. Dumb orchestrator** | Пуска `pipeline.py --priority auto` и pipeline сам решава | По-чисто разделение |
| **C. Orchestrator не знае** | Просто `pipeline.py --all` — regen всички | Сегашното поведение |

**Моята препоръка: A.** Orchestrator трябва да знае фокуса — това е смисълът на master worker.

### Q5: Data model — разширяваме ли `tasks_data.js`?

Проблем: `tasks_data.js` има само един `toolkit` на Task. Реално toolkit-ът **зависи от level**:

- Task 1 × Regional = `1.1-1.11`
- Task 1 × National = `2.1-2.12` (не е дефинирано в момента!)

| Опция | Какво | Pros / Cons |
|---|---|---|
| **A. Без промяна** | Derive from `TASKS_DATA.toolkit` (само regional) | Работи сега; не покрива national |
| **B. Разшири `tasks_data.js`** | Добави `toolkit_by_level: {0: [], 1: [...], 2: [...]}` | Ясно; изисква промяна в UI |
| **C. Derive от LEVELS groups** | Task 1 (geometry) = всички "Геометрия" групи от всички levels | Работи; но fragile (name matching) |

**Моята препоръка: B** — но не веднага. Първо пусни **A** (работи за regional, което е 109 дни напред). Ако решиш, че Task 1 national е приоритет, тогава разшири.

## 5. Предложен план за имплементация

### Фаза 1: `plan.py` (0 API, 45 мин)

1. Напиши `plan.py` — парсва 3 data файла, 6 API функции
2. Напиши `tests/test_plan.py` — 15 unit теста
3. Провери ръчно: `python -c "from plan import get_toolkit; print(get_toolkit(1))"`
4. **Не пипай нищо друго още** — plan.py е standalone

### Фаза 2: Интеграция в `pipeline.py` (0 API, 15 мин)

1. `pipeline.py --task 1` → филтър по `plan.get_toolkit(1)`
2. `pipeline.py --priority p1` → филтър по `plan.get_priority(1)`
3. `pipeline.py --level 1` → филтър по `plan.get_level_points(1)`
4. Тест: dry-run, виждаш правилните точки

### Фаза 3: Интеграция в `daily_verifier.py` (0 API + 1 API call)

1. `audit_task_completion(task_num, level_id)` → нов метод
2. Замени hardcoded week→phase с `plan.get_current_focus()`
3. Тест: 1 API call, виждаш отчета

### Фаза 4: Интеграция в `master_orchestrator.py` (0 API)

1. Прочети `plan.get_current_focus()` в началото на деня
2. Ако фокус = Task 1 → приоритет P1
3. Логика: ако `task_completion(1, regional)` не е complete → регенерирай P1; иначе P2
4. Тест: dry-run

### Фаза 5: Интеграция в `pdf_chunker.py` / `problem_generator.py` (0 API)

1. Замени `load_steps_info()` със `plan.get_all_points()`
2. Добави `--task` и `--priority` флагове
3. Тест: dry-run

### Фаза 6 (опционално, ако решиш): Разшири data model

1. Добави `toolkit_by_level` в `tasks_data.js`
2. Обнови `plan.get_toolkit(task, level)` да чете оттам
3. UI-ят може да покаже "Task 1 × National = 12 точки"

## 6. Какво НЕ променям

- `config.py`, `config.json` — остават
- Data файлове (освен ако Q5 = B)
- Съществуващите extract/classify стадии
- Статиите — само се регенерират, не се променя генерирането

## Какво трябва да решим преди да пиша `plan.py`

Отговори на 5-те въпроса:

1. **Q1 — target level:** calendar-driven, config, или UI?
2. **Q2 — "готов" значи:** article ready, anchors ready, full ready, или student-ready?
3. **Q3 — persist:** derived (fresh) или persisted (fast)?
4. **Q4 — orchestrator:** plan-aware, dumb, или doesn't know?
5. **Q5 — data model:** без промяна, разшири `tasks_data.js`, или derive от LEVELS?

**Моите препоръки (ако искаш просто да потвърдиш):**
- Q1 = A+B (calendar default + config override)
- Q2 = C (full ready — article + anchors + problems + verifier score)
- Q3 = A (derived)
- Q4 = A (plan-aware orchestrator)
- Q5 = A сега, B по-късно (ако решиш)

**Като ми кажеш отговорите, ще напиша:**
1. `plan.py` — 250 реда
2. `tests/test_plan.py` — 15 теста
3. `patch_pipeline_plan.py` — за инжектиране на `--task/--priority/--level` в pipeline.py
4. `patch_verifier_plan.py` — за audit_task_completion
5. `patch_orchestrator_plan.py` — за current_focus

Без да пипам нищо друго. Всяка стъпка е обратима (backup + restore).

## Ключов дизайн — `point_status.py`

Защо отделен файл вместо да се чете от `audit/<date>/report.json`?

**Защото "статус на точка" е composed от 5 източника:**

| Източник | Какво дава |
|---|---|
| `articles/_manifest.json` | `status: old/new` |
| `anchors/<point>.json` | `total`, `by_difficulty` |
| `problems/<point>/problems.json` | брой practice |
| `audit/<date>/report.json` | последен verifier score |
| `audit/<date>/report.json` | последен anchor accuracy |

Ако pipeline чете всички тези всеки път, става бавно и кодът се повтаря.

**Решение:** `point_status.py` има единствена функция `compute(point_id) → dict`:
```python
{
    "point_id": "1.4",
    "article": {"status": "new", "words": 3100, "sections": 9, "checks": 3},
    "anchors": {"total": 5, "verified": 4, "accuracy_pct": 80},
    "practice": {"total": 9, "easy": 3, "medium": 3, "hard": 3},
    "audit": {"article_score": 8, "anchors_score": 7, "audited_at": "2026-10-22"},
    "ready": True,           # всичките 4 условия Q2
    "blocking_issues": []    # кое липсва
}
```

Pipeline вика `point_status.compute(pid)` за да реши дали да генерира. Verifier вика `point_status.write(pid, {...})` след одит.
